# Hardened Wolfi runtime image (rootless, read-only-root compatible)

The production container adopts a Wolfi-based (`cgr.dev/chainguard/wolfi-base`), rootless (`USER 65532:65532`), read-only-root-filesystem-compatible runtime image, following the hardening standard used in `TomGrozev/bedrock-containers`. The runtime is now: non-root, unprivileged port (4000), no Linux capabilities, tini as PID 1, and scanned by Hadolint + Grype in CI. The build stage is `cgr.dev/chainguard/wolfi-base:latest` (the same free base the runtime uses) with OTP 28 installed from the Wolfi `erlang-28` apk and Elixir 1.20.3 from the official precompiled `elixir-otp-28.zip`, so the compiled OTP `crypto` NIF links against the same no-sm4 libcrypto the runtime ships. The runtime base is swapped from `debian:bookworm-slim` to Wolfi because Wolfi ships a glibc userland (preserving the pre-existing curl_cffi/yt-dlp impersonation requirement that originally drove the choice of `debian:bookworm-slim` over Alpine), while delivering a much smaller, actively CVE-patched image than Debian slim. Because the runtime dependency footprint is unchanged (the runtime still needs glibc + libssl + libstdc++ + ncurses + libsctp + ffmpeg + Python + pip), the yt-dlp/curl_cffi rationale that was already documented at the top of the Dockerfile carries over verbatim — only the base image name changes. All ephemeral runtime writes (yt-dlp fetch dir under `System.tmp_dir!()` from `lib/insta_mealie/ytdlp_cli.ex`, the Elixir release's `RELEASE_TMP`, and the BEAM VM's `~/.erlang.cookie` written via `HOME`) are consolidated under `/tmp`, so a single Kubernetes `emptyDir` mounted on `/tmp` is sufficient for a `readOnlyRootFilesystem: true` deployment — no other mounts are required, because InstaMealie has no database (jobs live in ETS per ADR 0001) and no persistent state. (Companion to the `bedrock-containers` hardening standard; resolves wayfinder ticket #15.)

**Considered Options**
- Stay on `debian:bookworm-slim` and just add USER/non-root ENTRYPOINT work — rejected: keeps a heavier, slower-to-patch base than Wolfi for no functional gain.
- Alpine / musl base — rejected: `curl_cffi` (required by yt-dlp `--impersonate`) has no musl prebuilt wheel and building it is fragile; the existing constraint comment in the Dockerfile already documents this.
- Wolfi (`cgr.dev/chainguard/wolfi-base`) + rootless + read-only-root consolidation — chosen.
- Also build on Wolfi (`cgr.dev/chainguard/wolfi-base:latest`, OTP 28 via `erlang-28` apk, Elixir 1.20.3 via the official `elixir-otp-28.zip`) instead of a Debian Elixir image — previously the build stage stayed on Debian as a "build-time concern", but that was wrong: the Debian-built OTP `crypto.so` referenced `EVP_sm4_cbc@OPENSSL_3.0.0` (SM4 enabled), which Wolfi's `no-sm4` libcrypto doesn't export, so the crypto NIF failed to load at runtime on every published tag. Building on Wolfi aligns the NIF with the runtime libcrypto and eliminates this class of ABI mismatch. The `cgr.dev/chainguard/elixir` image was rejected because it is premium/paid; Wolfi's native `elixir` apk was rejected because it is only Elixir 1.19 (too old for `mix.exs` `~> 1.20`).

**Consequences**
- Runtime image runs as UID 65532:65532, has no Linux capabilities, listens on port 4000 (>1024), and uses `tini --` for signal forwarding / zombie reaping.
- Build-time gate (`yt-dlp --list-impersonate-targets` failing the build when impersonation is unavailable) is preserved; a degraded yt-dlp cannot ship.
- yt-dlp is installed via a Python venv at `/opt/yt-dlp-venv` (Wolfi Python is externally-managed under PEP 668, so pipx is avoided and a venv is the cleanest isolated install path).
- The only writable paths under a `readOnlyRootFilesystem: true` deployment are `/tmp/insta_mealie/*` (yt-dlp fetch base + release tmp) and `/tmp/bedrock/home` (Erlang cookie). `entrypoint.sh` materializes these on every startup; no PVC is needed because no state is durable (ADR 0004).
- `~/.erlang.cookie` is ephemeral across restarts, which is fine for a single-node, non-clustered release (no dist / no epmd peer connections expected in the deployment target).
- The Wolfi base is pinned to `:latest` (intentional — see `.hadolint.yaml`'s DL3007 ignore); InstaMealie does not run Renovate, so the base image is bumped by manual PR. A real CVE-driven bump path is to follow `cgr.dev/chainguard/wolfi-base` upstream and open a PR.
- Hadolint runs on the Dockerfile in CI; Grype scans the built image and fails pushes to `main` on HIGH/CRITICAL findings (PRs report only). No `.grype.yaml` ignore list is fabricated here; if Grype surfaces an inherited finding, the user triages it explicitly per the issue brief.
- The build stage is now Wolfi-based (`cgr.dev/chainguard/wolfi-base:latest` with OTP 28 from the `erlang-28` apk and Elixir 1.20.3 from the official `elixir-otp-28.zip`) so the OTP `crypto` NIF is compiled against Wolfi's `no-sm4` libcrypto, matching the runtime. This corrects the earlier (wrong) assumption that the build stage was a build-time-only concern: the compiled NIF ships in the release, so build and runtime OpenSSL feature sets must match. The runtime stage and apk dependency footprint are unchanged. The build stage runs as root (needed for `apk add`); only the compiled release reaches the runtime via `COPY --chown=65532:65532`, so no root leaks to production.
